# Spec: Grade-Level Setup, Subjects, Lessons & Students-in-Grades

> Status: **Draft / Plan** — open questions in §11 still need your call, but
> the four decisions in the latest review pass are baked in (see §0).
> Owner: Students + Settings + Assignments + Core contexts
> Depends on: `landing-page-wrapper.md`, `multi-tenant-coded-values.md`,
> `coded-values-tenancy-impl.md`, `shared-coded-value-dropdown.md`,
> `auth-tenancy-integration.md`

## 0. Decisions locked in this revision

1. **Assignments pair to `GradeLevel.Id`, not a coded-value id.** `GradeLevel`
   is the **reporting source of truth**. The coded value (+ tenant override)
   only supplies the **display name**. (Replaces the old
   `Assignment.GradeCodedValueId`.) **By symmetry** (per review),
   `Assignment.SubjectCodedValueId` is also replaced by `Assignment.SubjectId`
   (FK → `Subject.Id`) in the **same migration** — `Subject` is the operational
   peer of `GradeLevel`.
2. **A real `Tenant` table (`Id` + `Name`) lives in the DB.** Confirmed absent
   today (only the three override tables exist), so this spec creates it. Tenant
   ids are generated by the **project convention** — the `Tenant.Create(...)`
   factory sets `Id = Guid.NewGuid()`, exactly like `GradeLevel.Create`,
   `Student.Create`, `Assignment.Create`. The seeder is **idempotent by `Name`**
   (the natural key) and resolves the generated id at seed time for related sample
   data. No hardcoded Guids.
3. **The period shown on a grade level is always the *current* period** — the
   one whose `[StartDate, EndDate]` contains today. It is **derived**, never
   picked. There is no period selector on the landing page.
4. **At most one active/current period per year.** A domain invariant: no two
   periods may have date ranges that both contain today (equivalently, at most
   one `PeriodStatus.Active` period whose range covers "now"). Enforced on
   `Period.Create/Update/Activate`.

These resolve open questions Q1 (approach A), Q2 (no picker — derived), Q4
(no current period ⇒ 0 + "No current period"), Q-new-1 (SubjectId — yes),
Q-new-2 (tenancy table — confirmed absent, create it), Q-new-3 (Guid convention —
`Guid.NewGuid()` via `Tenant.Create`, idempotent by Name). Remaining questions
in §11.

5. **`Tenants` DbSet on the existing central context** — `SettingsDbContext`
   (the existing concrete context that already hosts `User` + all tenant
   override tables; `ModuleDbContext` in Core is abstract/tenant-scoped, so it
   can't host the global Tenants table). No new DbContext.
6. **GradeLevel + Subject edit/delete are in scope now.** Both have `Update`
   commands but no `Delete` (no domain method, no endpoint) and no admin edit
   pages today — this spec adds delete + edit for both.
7. **Subjects landing page gets the full `<LandingPage>` migration** (not just
   filter plumbing), **always has a GradeLevel filter** (mandatory, not
   optional), and **creating a subject from the Subjects landing page always
   carries a `GradeLevelId`** (creates the `Subject` **and** a
   `GradeSubjectAssignment` for the current period).
8. **The Assignments Create subject control references the `Subject` table**
   (operational entities), filtered by the selected `GradeLevel` + the current
   period — so only subjects actually assigned to that grade are selectable.
   (Follows from decision 1's `SubjectId` migration.)

These resolve all prior §11 questions; see §11 for the (minimal) residual
items.

## 1. Goal

Establish grade levels as the **starting point** for setting up groups and the
thing assignments get paired to — with `GradeLevel` as the reporting source of
truth. Deliver a minimal, end-to-end setup flow for grade levels + students that
can be paired to assignments, plus a grade-level landing page with search,
create, per-current-period stats, and cross-navigation to the Students and
Subjects landing pages (with a filter pre-applied).

Two UX surfaces change, plus one data-model migration:

1. **The Grade-Level landing page** (`/students/grade-levels`) moves onto the
   shared `<LandingPage<TItem>>` wrapper with a search box and a Create tool,
   shows counts of students and subjects for the **current period** (derived
   from today's date), and lets each count deep-link into the Students /
   Subjects landing page filtered to that grade + the current period.
2. **The Grade-Level wizard** (`/students/grade-levels/create`) lets the user
   either pick an existing default grade coded value **or** create a new one
   **or** override the default grade name for the current tenant — all from a
   single dialog invoked from the coded-value selector. The wizard
   **finds-or-creates** the `GradeLevel` for the chosen coded value.
3. **Assignment → GradeLevel pairing.** `Assignment.GradeCodedValueId` is
   replaced by `Assignment.GradeLevelId` (FK to `GradeLevel`). The Assignments
   Create/Edit UI swaps the coded-value dropdown for a GradeLevel dropdown.

## 2. Non-goals (this spec)

- Rebuilding the Periods landing page onto `<LandingPage>` (separate
  follow-up). The Subjects landing page **is** migrated this spec (decision 7).
- Lessons (`SubjectLesson`) and Strands (`SubjectStrand`) admin UI. The data
  model is documented in §4 so the setup story is complete, but no
  lesson/strand pages ship in this spec.
- Promotions / period rollover (existing `PromotionService`).
- Migrating existing auth/claims to require the `tenant_id` claim to match a
  `Tenant` row (the table is the source of truth for tenant identity, but
  `ITenantProvider` keeps reading the claim; enforcement is a follow-up).

### 3.2 How assignments pair to grades (Assignments.Core) — **CHANGES**

Today `Assignment` carries:

- `SubjectCodedValueId` (Guid, required) — references the `SUBJECT` coded value.
- `GradeCodedValueId` (Guid?, optional) — references the `GRADE` coded value.
- `TargetAudienceType` enum: `AllStudents | SelectedGrades | SelectedGroups`.

**After this spec:**

- `GradeCodedValueId` is **removed**. Replaced by `GradeLevelId` (Guid?,
  optional, FK → `GradeLevel.Id`).
- `SubjectCodedValueId` is **also removed** (by symmetry, per review). Replaced
  by `SubjectId` (Guid, required, FK → `Subject.Id`).
- `TargetAudienceType` semantics unchanged; `SelectedGrades` now means
  "students enrolled in the selected `GradeLevel` for the current period."

**Rationale.** `GradeLevel` and `Subject` are the durable operational entities a
tenant actually groups students under. Pairing assignments to their `Id`s
(rather than the global coded values) gives stable reporting keys that survive
coded-value edits, and the display names are still tenant-resolved via the
coded value + `TenantCodedValueOverride` (so 'Hydeson School' can show "Standard 1"
while 'Little Legends' shows "Year 1" for the same `GradeLevel`).

### 3.3 Coded values + tenancy overrides (Settings.Core)

- Global blueprint: `CodedValue` (parent `GRADE` seeds `Grade R`, `Grade 1`…`Grade 8`…).
- Override: `TenantCodedValueOverride` { `TenantId`, `GlobalCodedValueId`, `OverriddenName?`, `OverriddenDescription?` }.
- Resolution: `ICodedValueResolver.ResolveAsync(cv, tenantId)` → `OverriddenName ?? cv.Name`. Already applied by `GetCodedValuesByParentHandler` (so `CodedValueDropdown` already shows tenant-resolved names).
- CQRS exists: `UpsertCodedValueOverride(globalCodedValueId, name?, description?)`, `RemoveCodedValueOverride(globalCodedValueId)`.
- **API gap:** no HTTP endpoint exposes coded-value overrides today (only config-flag overrides at `/api/config/flags/{key}/overrides/...`). The wizard's override dialog needs a new endpoint + client method (§5.1).

### 3.5 Tenancy model — **CHANGES**

There is **no `Tenant` table today** (confirmed across every `DbContext` —
`SettingsDbContext`, `StudentsDbContext`, `AssignmentsDbContext`,
`ModuleDbContext` — only the three override tables exist:
`TenantCodedValueOverride`, `TenantCodedValueAttributeOverride`,
`TenantFeatureFlagOverride`). Tenancy is purely claim-based:
`ITenantProvider.GetTenantContext()` returns a `TenantContext(TenantId, Name,
Type)` resolved from `tenant_id`/`tenant_name`/`tenant_type` claims
(`TenantClaimsTransformation`). `TestAuthHandler` authenticates every request
as a single hardcoded test tenant
(`00000000-0000-0000-0000-000000000001` / "Test Tenant"). There is no tenant
registry, no tenant switcher, and no per-tenant seed data.

**After this spec:** a `Tenant` table (`Id` + `Name` + `Type`, plus audit) is
introduced (§5.5) as the source of truth for tenant identity. The `Tenant.Id`
follows the **project Guid convention** — the `Tenant.Create(name, type)`
factory sets `Id = Guid.NewGuid()`, identical to `GradeLevel.Create`,
`Student.Create`, `Assignment.Create` (all use `Id = Guid.NewGuid()`).
`ITenantProvider` keeps reading the claim, but the claim's `tenant_id` now
corresponds to a real `Tenant` row. The seeder is idempotent by `Name`.
Sample tenants 'Hydeson School' and 'Little Legends' are seeded as the starting
point for testing overrides.

### 3.6 Landing-page wrapper

`<LandingPage<TItem>>` in `SchoolCollab.Admin.Shared.Components.Landing`
(see `landing-page-wrapper.md`). Slots we use: `Columns`, `ToolbarFilters`,
`ToolbarActions`, `SearchText`/`SearchTextChanged`, `CreateLabel`/`CreateRoute`,
`Items`, `Loading`, `EmptyMessage`, `Error`. `Students/Index.razor` is the
reference adoption (client-side search via a computed `_filteredItems`).

### 3.7 Gaps found (must be addressed by this spec)

1. `ListGradeLevelsHandler` counts `SubjectCount`/`StudentCount` **across all
   periods** with no period filter, and its cache key `"grade-levels:list"` is
   **not tenant-aware** (counts must be tenant-scoped via `Student.TenantId`;
   the display-name overlay is tenant-scoped via the coded-value override).
2. No API endpoint exposes `UpsertCodedValueOverride` / `RemoveCodedValueOverride`.
3. `Subjects.razor` / `Periods.razor` are not on `LandingPage` and have no
   query-string filter support, so the grade-level page cannot deep-link into
   them with a filter today.
4. `Students/Index.razor` search is client-side over a single loaded list; it
   has no "filter by grade level" entry point.
5. `Assignment.GradeCodedValueId` references a coded value, not `GradeLevel`
   (decision 1 — migrate to `GradeLevelId`).
6. `GradeLevel` has no uniqueness on `CodedValueId`; the wizard creates
   duplicates. Need a unique index + find-or-create.
7. No `Period` "current period" derivation or overlap invariant (decisions 3 & 4).
8. No tenant registry / sample tenants (decision 2).

## 4. Data model relationships (reference diagram — after changes)

```
CodedValue (GRADE)  ──blueprint──►  TenantCodedValueOverride  (per-tenant display name)
   │  (unique)
   └─► GradeLevel.CodedValueId        (GLOBAL operational entity; Id = reporting key)
          │
          ├──◄── Assignment.GradeLevelId   (reporting source of truth — NEW)
          │
          ├──► GradeSubjectAssignment ──► Subject (CodedValue SUBJECT)
          │           │                      │  (unique by CodedValueId)
          │           └── PeriodId           ├──◄── Assignment.SubjectId  (NEW)
          │                                  │
          └──► StudentEnrollment ──► Student  (tenant-scoped)
                      │
                      └── PeriodId

Tenant (Id=Guid.NewGuid(), Name, Type) ── source of truth for tenant identity
  ▲  TenantCodedValueOverride.TenantId, Student.TenantId, Assignment.TenantId …

Period  ── invariant: at most one period's [StartDate, EndDate] contains today
```

Reading: a **Grade Level** is the global operational grouping for a grade coded
value; its `Id` is the stable reporting key that assignments reference. For the
**current period** (the one containing today), a grade has **Subjects**
(`GradeSubjectAssignment`) and **Students** (`StudentEnrollment`, tenant-scoped).
The display name of a grade level is tenant-resolved from its coded value +
override, so the same `GradeLevel.Id` shows as "Standard 1" to 'Hydeson School'
and "Year 1" to 'Little Legends'.

| `DELETE` | `/api/coded-values/{id:guid}/override` | `RemoveCodedValueOverride` | — → `204` |

Authorization: same cookie/role gating as the other coded-value write routes.

### 5.2 Add client methods (SchoolCollab.Admin.Shared `CodedValuesApiClient`)


Consumed by the wizard's override dialog (§6.2) and, later, any reference-data

### 5.3 Current-period derivation + grade-level landing query (Students.Core)

The displayed period is **always the current period** — the `Period` whose
`StartDate <= today && EndDate >= today`. If none matches, there is "no current
period" and counts are `0`.

- New query `ListGradeLevelsForLanding` → `GradeLevelLandingDto[]`. **No
  `PeriodId` parameter** — the handler derives the current period server-side
  from today's date (so the UI can't get out of sync).
- `GradeLevelLandingDto` (new, in `Students.Core/DTOs`):

  ```csharp
  public sealed record GradeLevelLandingDto(
      Guid Id,
      Guid CodedValueId,
      int Level,
      string Name,              // mirrored name (display name overlaid client-side — §5.4)
      int DisplayOrder,
      int SubjectCount,         // GradeSubjectAssignments for (grade, current period) — global
      int StudentCount,         // active StudentEnrollments for (grade, current period) — tenant-scoped via Student.TenantId
      Guid? CurrentPeriodId,    // the current period these counts are for (null = no current period)
      string? CurrentPeriodName,
      DateTimeOffset CreatedAt,
      DateTimeOffset UpdatedAt);
  ```

- Handler derives `currentPeriod = db.Periods.FirstOrDefault(p => p.StartDate <= today && p.EndDate >= today)`.
  If `null`, counts are `0`, `CurrentPeriodId/Name` are `null`.
- **Tenant scoping of counts:** `StudentCount` joins `StudentEnrollment` →
  `Student` and filters `Student.TenantId == currentTenantId` (use
  `ITenantProvider`). `SubjectCount` is global (subjects are the shared
  curriculum blueprint). Cache key:
  `tenant:{tenantId}:grade-levels:landing:current-period:{currentPeriodId ?? "none"}`,
  tagged `students` + `tenant:{tenantId}` + `periods`.

### 5.4 Tenant-resolved display name (landing row)

`GradeLevel.Name` is a mirrored copy that goes stale on override. The landing
page overlays the resolved name **client-side** (approach A — keeps Students
context decoupled from Settings):

- The landing page calls `CodedValuesApiClient.GetChildrenByParentCodeAsync("GRADE")`
  once (already tenant-resolved) and joins by `CodedValueId` to replace
  `Name` with the resolved name for display.
- The underlying `GradeLevelLandingDto.Name` (mirrored) is kept for sort/fallback

No Students.Core → Settings.Core coupling. (Approach B — calling
`ICodedValueResolver` from Students.Core — is explicitly rejected.)

### 5.5 Tenant registry + sample seeding (Core + MigrationService) — NEW

Introduce a `Tenant` table as the source of truth for tenant identity
(confirmed absent today — §3.5):

- New entity `SchoolCollab.Core.Tenancy.Tenant` { `Id` (Guid), `Name`,
  `TenantType Type`, `CreatedAt`, `UpdatedAt` } implementing `IEntity`,
  `IAuditableEntity`. **Guid convention:** a `Tenant.Create(string name,
  TenantType type)` factory sets `Id = Guid.NewGuid()` — identical to
  `GradeLevel.Create`, `Student.Create`, `Assignment.Create`. **No hardcoded
  Guids.**
- Storage home: **`DbSet<Tenant> Tenants` on the existing `SettingsDbContext`**
  (decision 5) — the existing concrete context that already hosts `User` and
  all tenant-override tables (`TenantCodedValueOverride`,
  `TenantCodedValueAttributeOverride`, `TenantFeatureFlagOverride`). There is
  no concrete Core-project DbContext (`ModuleDbContext` is abstract +
  tenant-scoped, so it can't host the global Tenants table). `Tenant` does NOT
  implement `ITenantEntity`, so no tenant query filter is applied to it — it is
  globally queryable. Config via `EntityTypeConfigurationBase<Tenant>`; migration
  on the Settings context.
- **Seeder (MigrationService `TenantSeeder`), idempotent by `Name`** — mirrors
  `CodedValueSeeder`'s idempotency-by-natural-key pattern:
  - Load existing tenants into a `Name → Id` map. For each seed tenant not
    already present, call `Tenant.Create(name, type)` and capture the
    generated `Id`.
  - Seed `'Hydeson School'` and `'Little Legends'` (Type = `School`).
  - Because ids are `Guid.NewGuid()` per run, all **related sample data must
    be wired in the same seed pass** using the captured ids (not fixed Guids):
    `TenantCodedValueOverride.TenantId`, `Student.TenantId`, etc.
- **Sample data per tenant** to exercise tenancy overrides:
  - Both tenants share the global `GRADE` coded values (blueprint) and the
    single `GradeLevel` per grade (global, unique by `CodedValueId`).
  - `TenantCodedValueOverride` rows demonstrating different display names
    (keyed by the captured `tenantId` + the grade coded value id, looked up by
    code at seed time):
    - `Hydeson School` → "Grade 1" displayed as **"Standard 1"**, "Grade 2" → "Standard 2", …
    - `Little Legends` → "Grade 1" displayed as **"Year 1"**, "Grade R" → "Reception", …
  - One `Period` spanning today (so "current period" is non-empty in seed).
  - A few `Student` rows per tenant + `StudentEnrollment` into a grade for the
    current period (so `StudentCount > 0`).
  - A couple of `GradeSubjectAssignment` rows (so `SubjectCount > 0`).
- **Dev tenant switcher:** a small control in the admin shell (visible only in
  the `Testing` environment) that **lists tenants from the `Tenants` table by
  name** and sets the `tenant_id` claim to the selected tenant's `Id`, so a
  developer can flip between 'Hydeson School' and 'Little Legends' and see the
  overridden names + scoped student counts. (Auth wiring already supports
  per-request tenant via `TestAuthHandlerOptions.TenantId`; the switcher just
  changes which tenant id is used.) The existing test tenant
  (`00000000-…0001`) may optionally be seeded too for back-compat.

### 5.6 Period current-period invariant (Students.Core domain)

Enforce "at most one active/current period per year":

- `Period.Create` / `Period.Update`: reject if another `Period` exists whose
  `[StartDate, EndDate]` overlaps this one's range (so no two periods can both
  contain the same day). Throw a `PeriodOverlapException` (new, in
  `Domain/Exceptions`).
- `Period.Activate`: reject if any other period is already `Active`
  ( belt-and-braces; the overlap rule already guarantees a single current
  period, but the status invariant is cheap and clear).
- Migration: add a partial unique index or a runtime check (Postgres exclusion
  on `daterange` is the cleanest, but a repository overlap check is simpler
  and portable — implement in the handler, document the constraint).

### 5.7 Assignment → GradeLevel + Subject migration (Assignments.Core) — NEW

- Domain: replace `GradeCodedValueId` with `GradeLevelId` (Guid?, optional, FK
  → `GradeLevel.Id`) **and** replace `SubjectCodedValueId` with `SubjectId`
  (Guid, required, FK → `Subject.Id`). Update `Assignment.Create` /
  `Assignment.Update` signatures and the `AssignmentCreatedEvent`/
  `AssignmentUpdatedEvent` payloads.
- EF config (`AssignmentConfiguration.cs`): drop both coded-value columns, add
  `GradeLevelId` (nullable FK) and `SubjectId` (required FK). Migration
  `AssignGradeLevelAndSubjectToAssignments`.
- **Data backfill in the migration** (run **before** the column drops):
  - For each existing `Assignment.GradeCodedValueId`, find the `GradeLevel` with
    that `CodedValueId`; if it exists, set `GradeLevelId`; if not, **create**
    the `GradeLevel` (find-or-create) so no assignment loses its grade.
  - For each existing `Assignment.SubjectCodedValueId`, find the `Subject` with
    that `CodedValueId`; if it exists, set `SubjectId`; if not, **create** the
    `Subject` (find-or-create). (Requires the `Subject` unique index below.)
- Endpoints (`AssignmentRoutes.cs`) + contracts (`ContractTypes.cs`): rename
  `GradeCodedValueId` → `GradeLevelId` and `SubjectCodedValueId` → `SubjectId`
  on the create/update request DTOs and the summary DTOs.
- **Unique indexes (must run before the backfill so find-or-create is
  deterministic):**
  - `AddUniqueIndexOnGradeLevelCodedValueId`
  - `AddUniqueIndexOnSubjectCodedValueId` (new — `Subject` gains a unique index
    on `CodedValueId`, mirroring `GradeLevel`).
- **Assignments Create/Edit subject control** (decision 8): the subject dropdown
  lists `Subject` rows (operational), filtered by the selected `GradeLevelId`
  + the current period via `GradeSubjectAssignment` — so only subjects actually
  assigned to that grade are selectable. Add a `ListSubjectsByGradeAsync` client
  method + `GET /students/subjects/by-grade/{gradeLevelId}?periodId={guid?}`
  endpoint (also used by the Subjects landing page — §8).

### 5.8 GradeLevel + Subject edit/delete (Students.Core/Api/Admin) — NEW (decision 6)

Both have `Update*` commands but no `Delete` (no domain method, no endpoint)
and no admin edit pages today.

- **Domain:** add `GradeLevel.Delete()` and `Subject.Delete()` (hard delete —
  neither is soft-deletable; they're global reference entities). Guard deletes:
  reject if the grade/subject has `StudentEnrollment`/`GradeSubjectAssignment`/
  `StudentSubjectAssignment` rows or referenced `Assignment`s (throw
  `GradeLevelReferencedException` / `SubjectReferencedException`, new in
  `Domain/Exceptions`).
- **CQRS:** `DeleteGradeLevel(id)`, `DeleteSubject(id)` command + handler each
  (reuse existing `GetGradeLevelById`/`GetSubjectById` for the not-found case).
- **Endpoints:** `DELETE /students/grade-levels/{id:guid}` on
  `GradeLevelRoutes.cs`; `DELETE /students/subjects/{id:guid}` on
  `SubjectRoutes.cs`. Return `409` on referenced, `404` on not-found.
- **Admin:** add `GradeLevels/Edit.razor` (`/students/grade-levels/{id}/edit`)
  and `Subjects/Edit.razor` (`/students/subjects/{id}/edit`) edit pages using
  the existing `UpdateGradeLevel`/`UpdateSubject` commands + client methods.
  Row actions on both landing pages gain `Edit` (to the edit route) and
  `Delete` (confirm dialog via `DialogService.ShowConfirmationAsync`, then the
  DELETE call + optimistic removal + rollback on error).
- **Cascading consideration:** deleting a `GradeLevel`/`Subject` is blocked while
  any period-scoped assignment exists; document that the recommended lifecycle
  is to withdraw/un-assign first. (Soft-delete is a possible follow-up but not
  in this spec — keep the model honest with hard delete + referential guards.)

## 6. Wizard: create-new or override-existing grade name (dialog)

### 6.1 Step 1 redesign — coded-value selector + dialog

Replace the bare `<CodedValueDropdown>` in Step 1 with a selector that has
three affordances:

1. **Pick existing** — select a seeded grade coded value (current behaviour).
2. **Override name** — for the selected coded value, open a dialog to set a
   tenant-specific name (calls `UpsertOverrideAsync`). The dropdown refreshes
   and shows the overridden name. A "Reset to default" link calls
   `RemoveOverrideAsync`.
3. **Create new** — open a dialog to create a new child coded value under
   `GRADE` (code + name), then select it. Reuses `CodedValuesApiClient.CreateAsync`.

### 6.2 The dialog component

New shared dialog `GradeCodedValueDialog.razor` in
`SchoolCollab.Admin.Shared.Components` (sibling of `CodedValueDropdown`),
implementing `IDialogContentContent<GradeCodedValueDialogData>` (mirror
`AttributeDefinitionDialog.razor` in Settings.Admin for the pattern). Modes:

| Mode | Fields | Action |
|------|--------|--------|
| `Create` | Code*, Name*, DisplayOrder | `CodedValuesApiClient.CreateAsync` under parent `GRADE` |
| `Override` | Name (prefilled with default), Description? | `CodedValuesApiClient.UpsertOverrideAsync(codedValueId, name, desc)` |

### 6.3 Wizard save — find-or-create, current period

- **Find-or-create `GradeLevel`** by `CodedValueId` (now safe — unique index
  from §5.7): if a `GradeLevel` for the chosen `CodedValueId` exists, reuse it
  (and update mirrored `Name`/`Level`/`DisplayOrder`); otherwise create it.
  Add `StudentsApiClient.GetOrCreateGradeLevelAsync(...)` or a
  `GetByCodedValueIdAsync` + create fallback.
- **Period:** no longer "first Active period". Use the **current period**
  (derived server-side, same rule as §5.3). If there is no current period,
  block the subject/student assignment steps with a message ("Create a period
  covering today first") — subjects/students are period-scoped, so there is
  nothing to assign without a current period.
- Steps 2–4 otherwise unchanged in structure. Scope of this spec: the dialog
  in §6.2 + find-or-create + current-period wiring; do not rewrite the wizard
  scaffolding.

## 8. Subjects landing page + deep-link filter contract (Students & Subjects)

### 8.1 Subjects landing page — full `<LandingPage>` migration (decision 7)

`Subjects.razor` (`/students/subjects`) migrates onto `<LandingPage>`
`TItem = SubjectDto` (same pattern as Students/Index). Key behaviour:

- **A GradeLevel filter is always present** (mandatory, not optional). A
  `FluentSelect` of grade levels (loaded once, tenant-resolved names) lives in
  `<ToolbarFilters>`, bound to `_selectedGradeLevelId`. There is **no
  "all subjects" view** — the page always shows subjects for the selected
  grade + the **current period** (derived server-side, same rule as §5.3).
- On first load with no `?gradeLevelId=` query, default the select to the first
  grade level (or prompt the user to pick one if none exist).
- **Items:** `ListSubjectsByGradeAsync(gradeLevelId, currentPeriodId)` returns
  `SubjectDto[]` (join `GradeSubjectAssignment` → `Subject` for the current
  period). Search is client-side over those subjects.
- **Create tool (`+ New Subject`)** **always carries the selected `GradeLevelId`**
  (decision 7): the create flow creates the `Subject` **and** a
  `GradeSubjectAssignment(gradeLevelId, subjectId, currentPeriodId)` in one
  server call. New endpoint + client method:
  - `POST /students/subjects/for-grade` body
    `{ gradeLevelId, codedValueId?, code?, name, displayOrder }` → creates
    `Subject` (find-or-create by `CodedValueId` if provided, else from
    code/name) **and** the `GradeSubjectAssignment` for the current period.
    Returns the `SubjectDto`.
  - The create dialog is a `SubjectForGradeDialog` (mirror of
    `GradeCodedValueDialog`) or an inline form published into `CreateRoute`/
    dialog; it always sends the currently-selected `GradeLevelId`.
- **Row actions:** `Edit` → `/students/subjects/{id}/edit` (new, §5.8) /
  `Delete` (confirm + `DeleteSubject`, §5.8).
- A removable filter chip shows "Grade: <resolved name> · Period: <current>".

### 8.2 Deep-link filter contract (Students + Subjects)

So the grade-level stats navigate **with a filter applied**, both landing pages
accept query parameters and apply them:

| Route | Query params | Effect |
|-------|-------------|--------|
| `/students` | `gradeLevelId={guid}`, `periodId={guid?}` | Filter the student list to students enrolled in that grade for that period. |
| `/students/subjects` | `gradeLevelId={guid}`, `periodId={guid?}` | Pre-select that grade in the mandatory filter; load its subjects for the current period. |

Implementation notes:

- Parse query in `OnParametersSetAsync` (use `[SupplyParameterFromQuery]` in
  .NET 10). Store the filter, pass it into the load call.
- **Students:** add `ListStudentsByGradeAsync(gradeLevelId, periodId?)` to
  `StudentsApiClient` + endpoint
  `GET /students/by-grade/{gradeLevelId}?periodId={guid?}` returning
  `StudentDto[]` (active enrollments joined to `StudentEnrollment`, tenant-scoped).
- **Subjects:** `ListSubjectsByGradeAsync` + endpoint
  `GET /students/subjects/by-grade/{gradeLevelId}?periodId={guid?}` returning
  `SubjectDto[]` (join `GradeSubjectAssignment` → `Subject`). Also used by the
  Assignments Create subject dropdown (decision 8 / §5.7).
- `periodId` from the grade-level page is always the **current period id**
  (already derived server-side and carried on the DTO). Subjects ignores a
  passed `periodId` and re-derives current (single source of truth).
