### Design decisions (each: decision + one-line why)

1. **Worker project shape + AppHost + config.** New `src/Assignments/SchoolCollab.Assignments.Worker` (net10.0, `Microsoft.NET.Sdk` Exe) referencing `Assignments.Core` (+ transitively Core/Contracts), registered in AppHost as `assignments-worker` with `WithReference(assignmentsDb, rabbit, settingsApi, studentsApi)` + `WaitFor(rabbit)` + `WaitForCompletion(migrator)` and `RabbitMq__Subscriber__ExchangeName = assignmentsOutboxExchange` — mirroring the `students-worker` block (AppHost Program.cs ~228). Config stays centralized: **no new feature flag and no scattered appsettings** — the worker has a minimal local `appsettings.json` only for connection-string/section defaults exactly as `Students.Worker` does (repo-policy precedent), and no new `Parameters:` entries are needed (existing `outbox-exchange-assignments` is reused). Why: same-context worker per the Students precedent; repo policy forbids per-service flag values.
2. **Tenant enumeration in a background context.** Reuse the existing sanctioned sweep pattern verbatim: cross-tenant candidate reads on `AssignmentsDbContext` with `.IgnoreQueryFilters(["Tenant"])` (repository methods return `(Id, TenantId)` candidate records), then each candidate executes inside `ITenantContextAccessor.RunWithExplicitTenantAsync(candidate.TenantId, ...)` (mirror of `ArchiveSweeper`/`NotificationDispatchService`) — no HTTP request, per-candidate error isolation, cancellation-aware. Why: this is the established, tested posture for background tenant work in this repo.
3. **Unique index + dedupe.** The index must be **partial**: `CREATE UNIQUE INDEX ux_notification_logs_publish_uniqueness ON notification_logs (tenant_id, assignment_id, recipient_id) WHERE kind = 0` — a full `(…, Kind)` index would outlaw the legitimate multiple `Reminder`/`Overdue` rows per recipient over time (cadence sends one row per send), so only the `Publish` kind (the F1 duplicate class) is constrained. **Migration step order: dedupe THEN index** (single migration `DedupeNotificationLogPublishRows` in `Assignments.Core/Migrations`): `Up()` (1) deletes duplicate `Publish` rows keeping per key the row with the **latest activity** — greatest `UpdatedAt`, tie-broken by highest `Attempt`, then `Id` (the republish row carries the re-minted deep-link token, so latest wins) — then (2) creates the partial unique index; `Down()` drops the index only (deleted rows are not restorable — documented one-way data transform, accepted risk, per `ef-migrations.md` rule 4/8 the reverse that exists is provided). Insert paths after the index: the broadcaster's republish path changes from insert-always to **upsert-in-place** — for each recipient it now looks up the existing `Publish` row for the key and, if present, updates its rendered payload (`ToAddress/Subject/BodyHtml`), resets `Attempt = 0`, and re-queues (`DeliveryStatus = Queued`, `NextRetryAt = now`) instead of inserting — so a republish re-notifies with the fresh token without violating the index; the drain (`NotificationDispatchService`) is unchanged (it mutates rows in place, never inserts, so it cannot violate the index). Why: the index is a backstop, not the mechanism; idempotency belongs in the insert path.
4. **Outbox/event inventory + completion trigger.** Consumed event: **only `AssignmentPublishedIntegrationEvent`** (unchanged contract, per the breakdown) via the Core `AddRabbitMqSubscriber` + an `IIntegrationEventHandler<AssignmentPublishedIntegrationEvent>` that kicks the reminder sweep pass immediately after publish (so the first reminder evaluation doesn't wait a full sweep interval). **No submission/sign-off event exists** in `Assignments.Contracts`, and adding one is out of scope — the completion-to-guardian trigger is therefore **sweep-driven**: poll published assignments whose submissions sit in `SignOffState.AwaitingSignature` and queue a `Kind.Completion` row to the signing guardian contact (one per submission, suppressed by an existing non-terminal `Completion` row). Why: the breakdown pins E3 to the unchanged Published event; an event-driven completion trigger is recorded as a residual.
5. **Sweep scheduling + idempotency.** Two `BackgroundService`s copying the `ArchiveSweepService` loop shape (pure dispatch core in a static sweeper class, first sweep immediately, per-candidate isolation, `Task.Delay(Interval, stoppingToken)` cancellation): `ReminderSweepService` every **15 min** (reminder + completion checks; `ReminderIntervalHours` granularity ≥ 1h makes 15 min latency acceptable) and `OverdueSweepService` every **60 min**. Idempotency: sweeps are state-driven and re-run-safe — a recipient is only queued if no **non-terminal** (`Queued`/`Sent`) `NotificationLog` row of the required kind exists within the current cycle (reminders also capped by `MaxReminders` sent/queued rows per (assignment, recipient)); a crash mid-batch simply re-evaluates next pass. Overlap protection: single-worker-instance assumption as for all existing sweeps (dev deployment shape); the partial unique index additionally protects the `Publish` class from any double-broadcast race. Cancellation: all loops and per-candidate dispatch honor `stoppingToken`; `OperationCanceledException` on the delay is a clean shutdown (existing pattern).
6. **Reminder cadence resolution.** Cadence comes **entirely from the stored policy fields** via the existing `INotificationPolicyResolver` chain: first reminder due `ReminderIntervalHours` after publish (or after the submission entered `AwaitingSignature`, whichever is later), repeated every `ReminderIntervalHours` until `MaxReminders` `Sent/Queued` reminder rows exist or the ward/guardian state resolves (submitted / signed / assignment closed-archived); unresolved/absent policy (`null`) falls back to the built-in defaults already produced by `EffectiveNotificationPolicyResolver` — no new policy field, no spec-invented default values. Suppression interacts with the log: reminder dedupe is a **query** on existing `Reminder` rows (count + last-sent timestamp), not the unique index (which deliberately does not cover `Reminder`). Why: the spec's "24h/72h/day-of-due-date" values are illustrative and nothing stores them; the policy fields the breakdown calls "already stored" are `ReminderIntervalHours`/`MaxReminders`.
7. **Scope boundary.** Already ships and stays put: **auto-archive sweep** (`ArchiveSweepService` + `ArchiveSweeper` in `Assignments.Api` — Phase 4 row says so; moving it to the worker is pure churn), the **delivery drain** (`NotificationDispatchService` + Api `NotificationDispatchSweepService` — two drains would double-send), the **scheduled-publish and staged-file sweeps**, and `NotificationKind`'s enum members. E3 adds **only**: the worker host (reminder sweep incl. unsigned/incomplete, completion-to-guardian, overdue sweep), the Published-event subscription, the message-builder templates for the three new kinds, the new repository candidate reads, the partial unique index + dedupe migration, and the broadcaster upsert fix. Explicitly out: new integration events, moving any existing sweep, ward-list/guardian UI changes, ar-17 residuals other than the index (missing API-side enum converter registration, `Failures (N)`, multi-ward row labeling stay carried).
