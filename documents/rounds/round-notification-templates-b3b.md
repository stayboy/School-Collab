## Workstreams

**WS0 — the tag set moves to the shared kernel (Q90a).**
`NotificationTemplateTags` → **`SchoolCollab.Core.Abstractions`** (namespace `SchoolCollab.Core.Notifications`, beside `NotificationChannel` — `Core.Abstractions/NotificationChannel.cs:3`, which is this feature's cross-context vocabulary; the plan's first pick, `SchoolCollab.Core`, hosts *policy machinery* instead, and Abstractions is the maximal-visibility shared project: Admin.Shared and the mobile head both see it). The class is zero-dependency static, so the move changes no wire and no behaviour. `NotificationTemplateRenderer` already carries `using SchoolCollab.Core.Notifications;` (`:4`) and keeps `Assignments.Core.Domain` for `NotificationKind` — **the only churn is in `NotificationTemplateRendererTests.cs`**. A test pins `All` == the §3.2 set in spec order and that `Canonicalize` still resolves the Round-A aliases; an alias-using template must render byte-identically before and after.

**WS1 — the editor page (`Settings.Application`, route `/notification-templates`).**
1. Shell: kind tabs (Publish / Reminder / Completion / Overdue) × channel tabs (Email / SMS), mirroring `ConfigFlagDetail`'s shell posture (save / reset / reason / audit), **not** `LandingPage` (this is not a list). Authorization mirrors `/config-flags`: host-level OIDC, **no per-page policy** (`ConfigFlagDetail.razor` carries no `[Authorize]`, and §3.10 is silent).
2. **Master–detail per slot — the post-B2c substrate.** A slot holds **several rows** (B2c relaxed the index; only a second *unconstrained* row conflicts), and the client is list + by-id CRUD. So each kind × channel tab shows the slot's rows from `ListAsync` (each with `IsDefault` and its constraint summary), one editing pane for the **selected** row, a **“+ add template”** that calls `CreateAsync`, and a per-row **reset** that calls `DeleteAsync(id, reason)`. Without this the constraints editor and the conflict warning are unreachable — a single-record editor cannot express a second template. **Selection state, pinned:** on tab entry the slot's **default row is selected when one exists, otherwise the add state**; an **empty slot** shows “the built-in default applies” plus the add affordance; a slot whose rows are **all constrained** (no tenant default) shows a **“no tenant default — the built-in default applies to unconstrained sends”** note above the row list. Those three presentational states are part of the contract, not a worker's invention, and each has a WS4 case.
3. Email tab: `FluentTextField` subject (tags allowed) + `RichInstructionEditor` body (existing restricted toolbar, placeholder param). SMS tab: `FluentTextArea` + rendered-length guidance (warn near/over 160 chars — **never** a hard block, because tags expand at render time); when the preview is degraded the hint falls back to the **raw** authored length with a “rendered length unavailable” note rather than disappearing.
4. Constraints editor: five dimensions (grade levels, streams, activity groups, subject/topic, assignment type) with pickers from the existing codebook sources; adding a second template with an **identical constraint set** for the same kind × channel surfaces the §3.7 conflict warning (a warning, not a block — B2c's 409 is only about the *default*). **`Value` encodings are pinned to the matcher's own** (`AssignmentTemplateContext`): the four entity dimensions (GradeLevel, Stream, ActivityGroup, Subject) carry the **target reference id in `Guid.ToString("D")`**, and `AssignmentType` carries the **enum name**. A wrong encoding (a codebook *code* instead of the id, say) compiles, round-trips every bUnit test and then silently never matches at publish — so this is stated, not left to discovery.
5. **The `?grade=` receiving end (§3.11).** The page reads a `grade` query parameter and filters **each tab's row inventory** to the §3.11 applicability rule — `GradeLevel` absent **or** containing this grade id, compared trimmed + `OrdinalIgnoreCase` (B3a's `AppliesToGrade` semantics, so the card and the editor agree) — while the **4×2 tab shell stays unchanged** (every kind × channel remains reachable; the filter narrows rows, never tabs). The **`GradeLevel` constraint is pre-filled** with that grade on “+ add template”, so the card's deep link keeps its promise (“creating a grade-specific template is one click”).
6. **Live preview — the round's one design decision.** The renderer is cross-context, so the preview is a **new Assignments API route**: `POST /assignments/notification-templates/preview` taking **`NotificationTemplatePreviewRequest(kind, channel, subject, body)`** (no constraints — `ResolvedNotificationTemplate` consumes only subject/body) and returning the rendered pair; **enums travel by name** (this feature's established wire precedent). It renders against a **documented sample `NotificationTagValues` fixture**, including a **channel-appropriate sample link** (`Link` is the long email URL for Email and the short `/l/{code}` form for SMS — §3.2), because that is the one sample bit a preview can get visibly wrong. Rejected: moving the renderer into the kernel (it drags `NotificationKind`, `NotificationTagValues`, `ResolvedNotificationTemplate` and the built-in texts — `adr-cross-module-calls.md` puts **originator hops out of scope**, which this is), and re-implementing substitution in the UI (§3.10 demands the *exact* path, and a second substituter is the drift class this repo keeps paying for). **No better seam exists.** Client home: `Admin.Shared` (the nine-client home), registered beside `Settings.Application/ModuleServices.cs:86` with `AddCrossModuleHttpClient<…>("https+http://assignments-api", propagateTenant: true)` — the Admin host already carries `.WithReference(assignmentsApi)` (`AppHost/Program.cs:566`), so **no AppHost change**. The call gets an explicit **~5 s timeout** so the degradation note appears in seconds, not after the 100 s default; a failure shows an inline “preview unavailable” note and **never blocks save**.
7. Save sanitizes via `RichInstructionSanitizer` (the instruction-editor posture) → `NotificationTemplateApiClient` create/update-by-id; the **audit panel** reads `GetAuditAsync(kind, channel)` for the selected slot (already shipped by B3a).

**WS2 — the grade-detail applicability card (`Students.Application`).**

## Risks

- **A multi-row slot, not a record.** The editor's shell is master–detail because B2c made a slot a *set*; a single-record build would compile, look plausible, and leave the constraints editor and conflict warning unreachable. The slot-inventory test is what proves the shape.
- **Two surfaces, one client, one host.** The card relies on the client registered by `Settings.Application`; if the Admin host ever stops composing both modules, the card breaks at runtime, not at compile time. Mitigation: the card's bUnit test resolves the client from the composed container the same way the host does.
- **The preview seam is a cross-context call.** It must stay an enrichment read with a visible degradation and no save-path dependency; any attempt to make the preview authoritative would repeat the "sync write-path hop" mistake the architecture rules forbid.
- **A 67 KB page.** The card is a component rendered from `Detail.razor`; the diff to that file must be a single component invocation, not new logic.
- **Tag-set move.** The new home is `Core.Abstractions`, reached transitively via the already-referenced `Admin.Shared`; `Students.Application` does not reference it at all, so if the card ever needs tags that reference must be added deliberately rather than by transitive accident.
