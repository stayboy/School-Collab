### Goal

D19: **the teacher portal adopts the portal-session path.** The teacher signs in through the auth portal's existing surfaces (D6 password handshake / D16 passkey handshake), holds only an opaque session-id cookie in its own name (D12), renders identity from the D18 session read **as data**, and presents `X-Portal-Session` (`PortalSessionAuthenticationHandler.SessionHeaderName`, `src/SchoolCollab.Auth/Auth/PortalSessionAuthenticationHandler.cs:62`) on every call to the Assignments API. That API resolves the header through the `PortalSession`/`PortalSessionGateway` schemes, so the teacher-portal reader policy (`RequireAssignmentReader`, `src/Assignments/SchoolCollab.Assignments.Api/AssignmentEndpoints.cs:88-103`) authorizes the **same D9 claim set** (tenant + `teacher_id` + realm roles as `ClaimTypes.Role`) as the cookie/bearer paths. No credential, token or secret ever reaches Python (AC9/AC11 carry over verbatim); a `session ended` read clears the cookie and renders an AC10 card.

### The placement decision (Q4) — **(a): the handler + gateway move to `SchoolCollab.Core`**

Custody mechanics verified first, because they decide the fork: `PortalSessionStore` is a **process-local singleton in the auth service** (`AuthServiceExtensions.cs:68`). No remote host can ever resolve the D15 seam in-process, so **any** host that adopts the scheme needs an HTTP claims read against the auth service — that cost is identical for both fork options and is not a differentiator. What differs is where the handler type lives.

**Option (a) — Core move (chosen).** Move `PortalSessionAuthenticationHandler` + `PortalSessionAuthenticationOptions` to `src/SchoolCollab.Core/Auth/` (the `TestAuthHandler` precedent). It drags, and the plan owns:

- The handler's DI dependency `IAuthProvider` (Auth-only) is replaced by a **new, narrow Core port**: `IPortalSessionClaimsReader` with one async member `ValueTask<PortalClaims?> ReadClaimsAsync(string sessionId, CancellationToken)`. The D15 seam keeps its seven members untouched; the auth service registers the port as a trivial adapter over `IAuthProvider.ReadClaims` (genuinely I/O-free there).
- `PortalClaims` and the five claim-name constants (`ClaimSetFactory.cs:9,30-34`) move to Core with the handler — the D9 mapper contract keeps one spelling; `ClaimSetFactory` (which stays in Auth) references Core's record/constants (Auth → Core is the allowed shared-kernel direction, D2).
- `HandleAuthenticateAsync` becomes async (the remote port is async; the auth-service adapter is sync-under-async). Fail-closed semantics are unchanged: absent header, unknown session, incomplete claim set → `NoResult`; the challenge stays a bare 401 (`handler :122-146`).
- The gateway gains a **pinned fallback scheme** — **hardening, not rescue**: existing bearer callers are already authenticated by the group-level Bearer policy (`AssignmentEndpoints.cs:17-24`), so a host-default fallback (`SelectAuthenticationScheme`, `handler :70-84` → the OIDC **Cookie** under real auth, `AuthTenancyExtensions.cs:152`) could not 401 them; the pin exists because the reader policy's challenge must route non-portal API callers to a scheme that authenticates them correctly, and the host default is semantically wrong for an API host. The Core registration extension therefore takes an optional `fallbackScheme`; when null, today's host-default resolution is preserved (the auth service's registration is byte-for-byte equivalent in behaviour). Assignments pins `BearerScheme` under real auth and `TestAuthExtensions.TestAuthScheme` under `FEATURE:DisableOIDCAuth` — the **selector** resolves the flag at request time from `IConfiguration` via `context.RequestServices` (the same resolution pattern `SelectAuthenticationScheme` already uses; absent/invalid ⇒ fail-closed real-auth ⇒ Bearer), so the registration signature stays `(AuthenticationBuilder, string? fallbackScheme = null)` and Assignments' `Program.cs` adds no flag knowledge. **Precision:** the gateway's *challenge* is pinned to `PortalSession` (bare 401) regardless of the fallback — the fallback governs **authentication routing**, not the challenge; the pin restores today's exact Bearer-authentication union for bearer callers, which the host default would substitute with Cookie.
- The handler's **in-process** tests migrate to `tests/SchoolCollab.Core.Tests.Unit/Auth/` (beside the existing Core.Auth tests) — **self-contained**: Auth.Tests.Unit's helpers (`BuildProvider`/`JwtWithClaims`/`FakeTimeProvider`/`ScriptedHandler`) are cross-assembly and get rewritten locally, and the `ClaimSetFactory.*` constant assertions become the Core spelling; the three host-level tests **stay** in `Auth.Tests.Unit` (they need `AuthEndpointTestHost`/`PortalSessionStore`/`IAuthProvider` — unreferenced from Core.Tests.Unit); `IAuthProvider.cs:163` and `KeycloakAuthProvider.cs:159,451` take using fixes, `KeycloakAuthProviderTests.cs:423-425`'s pinned-constant assertions update to the Core spelling, and `MediatedReadEndpoints.cs` + `AuthEndpointGroup.cs` keep compiling against the moved type (namespace/using updates only).

**Option (b) — Assignments-side HTTP handler (rejected).** A new handler in `SchoolCollab.Assignments.Api/Auth/` (~200 lines duplicating handler + gateway + selector), a **third** spelling of the `X-Portal-Session` literal — the Python portals pin it precisely because the auth service was "the only other half of the contract … a rename on either side must break loudly" (`src/SchoolCollab.AuthPortal/api/admin_api_client.py:60-63`) — plus the *same* new claims route and HTTP reader that (a) needs anyway. D2 is honoured by both, but (b) multiplies spellings, repeats for the ward portal later, and still drags the scheme/header constants into Core for sharing. The grill's preference for (a) survives the custody verification.

**The registration diff shape for the Assignments API:**

- `AddAuthAndTenancy` itself is **unchanged** — adoption is an **opt-in extension**, not a change to the shared registration. The new Core extension (`AddPortalSessionAuthentication`) registers the `PortalSession` scheme + the `PortalSessionGateway` policy scheme (`ForwardChallenge = PortalSession`, bare 401) **in every flag state** — the gateway doc constraint (`handler :55-59`).
- `RequireAssignmentReader` swaps `AddAuthenticationSchemes(AuthTenancyExtensions.BearerScheme)` → `AddAuthenticationSchemes(PortalSessionAuthenticationHandler.GatewaySchemeName)` — ONE scheme, registered in both flag states, so the challenge can never 500. Portal callers route to `PortalSession`; bearer callers to Bearer (fallback); dev callers to TestAuth (fallback). The group-level policy at `AssignmentEndpoints.cs:17-24` and the ward/activity-groups policies are untouched — under real auth the combined group+reader policies authenticate the portal call via the gateway (Bearer `NoResult`s, the merged principal satisfies `RequireAuthenticatedUser`); under dev flags no policy applies, today's posture.
- `Program.cs` (Assignments.Api) adds the extension call + `AddCrossModuleHttpClient<PortalSessionClaimsReader>("https+http://auth", propagateTenant: false)` — the **generic overload takes only the base address** (`CrossModuleHttpClientExtensions.cs:26-29`; the plan's earlier `("auth", …)` spelling matched no overload); the Aspire service literal lives in the base-address expression, matched by the new `.WithReference(auth)` and the `CrossModuleWiringTests` contract. The client mirrors the ar-24 posture (`AllowAutoRedirect=false`, strict-2xx + content-type guard) and is **fail-closed**: transport failure, 404, non-JSON ⇒ `null` ⇒ `NoResult` ⇒ 401. An auth-service outage therefore 401s portal callers (the portal renders its AC10 card) — it never fails open.

**Per-request latency note (accepted):** every portal-authenticated assignments call adds one assignments→auth HTTP hop. Accepted because **fail-closed is the correct posture for an auth decision** — an auth-service outage must 401 the caller, never fail open — **not** because a read-hop ADR's "degrade gracefully" clause applies (it does not: this hop's failure fails the operation, deliberately). No caching in v1 (a possible later optimization, out of scope).

### Session bootstrap design — the teacher portal's own cookie

**Chosen:** a dedicated callback route on the teacher portal, `GET /auth/callback?code=…`, plus **one new auth-service route**, `POST /auth/handshake/session`, that redeems a **D6 handshake code** for the opaque session id — mirroring `PasskeyEndpoints.BootstrapRedeem` (`:228-271`) but over the handshake `OneTimeCodeStore` instead of the bootstrap store, so the two code namespaces stay disjoint exactly as built.

Why nothing existing suffices (code evidence): `/auth/redeem` returns **claims only** and is documented never to hand out a session id (`RedeemEndpoints.cs:17-19`); `/auth/bootstrap/redeem` yields a session id but its codes are minted only on the passkey path and bound to the single auth-portal bootstrap URI (`PasskeyEndpoints.cs:216` + `Auth:Portal:BootstrapRedirectUrl`) — a second portal cannot land there. The D6 code, by contrast, is already minted **bound to the caller's redirect URI and carrying the session reference** (`ExchangeEndpoints.cs:103`), so a session-yielding redemption over the handshake store is the minimal generalization: ~50 lines, no custody change, single-use + TTL + URI-binding semantics inherited from the store.

**Password path:** unauthenticated `/teacher*` → 302 to the auth portal's login page with `return_uri = {teacher-portal public base URL}/auth/callback` (the auth portal already renders + exchanges for any allowlisted `return_uri`). The exchange mints the D6 code bound to that callback; the auth portal 302s the browser to `{callback}?code=…`; the callback posts `{code, redirectUri}` to the new route, receives `{sessionId}`, sets the teacher portal's **own** D12 cookie, and 302s to `/teacher`. The session id the callback receives is the same one the auth portal set in its own cookie — one custody session, two cookies, no orphaned sessions.

**Passkey path — zero extra server surface:** the teacher portal's passkey handoff passes `app_redirect_uri` = the same `/auth/callback` URI (allowlisted). `PasskeyEndpoints.Complete` sees a non-portal-origin sign-in (`IsPortalOwnSignIn` origin comparison), mints the D6 continuation for that callback, and the auth portal's `/bootstrap` (`app.py:735`) re-validates the continuation against its own allowlist copy and 302s the browser to `{callback}?code=<D6 code>` — landing on the **same** redemption. (The teacher picks up an auth-portal session cookie along the way — harmless, documented.)

**Cookie:** its own name `school_collab_teacher_session`, HttpOnly + SameSite=Lax + Secure-over-HTTPS, mirroring the auth portal's `_set_session_cookie`. **Pitfall recorded:** on `localhost` cookies ignore ports, so the auth portal's cookie is *also* sent to the teacher portal's origin in dev — the teacher portal reads only its own cookie name and never relies on the sharing.

**Logout:** `GET /teacher/logout` mirrors the auth portal's `/logout` (D13 option ii): revoke via `DELETE /auth/session/{id}`, clear the cookie, 302 the browser to the returned `end_session` URL **as an opaque string** — never parsed, logged or persisted. **Recorded consequence:** `post_logout_redirect_uri` is `Auth:PostLogoutRedirectUri` — the **auth portal's root** (`Program.cs:497`) — so a teacher-portal logout lands on the auth portal afterwards; accepted rather than widening the pinned parameter set (the no-new-parameter rule).

**D18 rendering:** teacher surfaces render identity from `GET /auth/session/{id}` as data; `410 session_ended` and `404 session_not_found` both clear the cookie and render an AC10 card at HTTP 200; a degraded (unreachable) read renders the card **without** clearing the cookie (the session state is unknown, D18).

**Portal-side gate — one pinned rule ladder (no ambiguity):** (1) **session cookie present** → the session path: `X-Portal-Session` on every assignments call, identity from the D18 read; a dead session (`410`/`404`) clears the cookie and renders the AC10 card (never a redirect); a degraded read renders the card **without** clearing the cookie. `resolve_dev_teacher_id` is **never invoked** on this path — the session's `teacherId` is the only fallback, so a valid session can never be degraded by a dev-env gap. (2) **no cookie** → route semantics are today's, byte-for-byte: `resolve_dev_teacher_id` runs exactly where today's code runs it (the review-queue `teacherId` fallback), `MissingConfigurationError` refusal intact, **no header** — the dev id is **never** the gate's trigger, and routes that don't use it today render exactly as today. (3) **the gate's redirect is target-keyed, not dev-id-keyed**: scoped to the teacher-surface routes (`/teacher*` — the ward route is untouched), the gate acts only when no session cookie is present **and** `PORTALS_LOGIN_URL` is configured — then 302 with `return_uri` = the callback; with no redirect target (the dev posture — the env absent) **the gate does not act** and the request continues per rule 2, rendering today's honest views/cards — never an invented URL. A live-but-non-teacher session is not the portal's problem: the API's 403 renders as the degraded card (T4 — the API is the boundary; **no Python role list**). The auth portal's `require_admin_session` card shape is mirrored **only** for the dead-session card, never as a hard entry gate.

**Dev-bypass coexistence (D4):** the session mechanism is **flag-agnostic** — the gateway and scheme are registered in every flag state, so a portal session works under dev flags too (real claims from custody even while TestAuth auto-authenticates everyone else). With `FEATURE:DisableOIDCAuth` ON and no session cookie, the portal behaves exactly as today: `PORTAL_DEV_TEACHER_ID` supplies the review-queue `teacherId` fallback (inert under real auth, where the claim wins — round `portal-teacher-surface` D5), and `resolve_dev_teacher_id`'s `MissingConfigurationError` refusal is untouched. With the flag OFF, a session-less call 401s at the API and the portal renders its signed-out state. The portal never *substitutes* the dev bypass for real auth (D4): the bypass is only the no-session dev path.
