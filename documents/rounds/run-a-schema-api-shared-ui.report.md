### Backfill 1 — `periods.sequence` (verbatim)

```sql
WITH siblings AS (
    SELECT id,
           tenant_id,
           parent_period_id,
           division,
           start_date,
           substring(name from '([0-9]+)[[:space:]]*$') AS trailing_digits
    FROM periods
    WHERE division <> 0
),
positioned AS (
    SELECT id,
           COALESCE(
               CASE
                   WHEN length(siblings.trailing_digits) <= 9
                       THEN siblings.trailing_digits::int
               END,
               (row_number() OVER (
                    PARTITION BY siblings.tenant_id, siblings.parent_period_id, siblings.division
                    ORDER BY siblings.start_date, siblings.id
                ))::int
           ) AS sequence
    FROM siblings
)
UPDATE periods
SET sequence = positioned.sequence
FROM positioned
WHERE periods.id = positioned.id;
```

* End-anchored parse (`[0-9]+[[:space:]]*$`) — `"2027 Term"` matches nothing and falls through to
  the positional rule, which is the whole point of Q8a.
* The cast is guarded twice: `substring(...)` returns NULL when there is no match, and the
  `CASE` refuses any digit run longer than 9 characters, so `"Term 99999999999"` yields NULL and
  falls through instead of aborting the migration with `value out of range`. `CASE` only
  evaluates the branch it takes, so the cast never runs on a row it would fail on.
* `division <> 0` is the only scope guard: top-level academic years keep `sequence = NULL`, which
  is exactly what makes the `filter: "sequence IS NOT NULL"` partial unique index correct
  (Postgres treats NULLs as DISTINCT — the same trap the exception's COALESCE expression indexes
  work around, answered here with a partial index instead of an expression index).

### Backfill 2 — `subject_enrollment_exceptions.ordinal` (verbatim)

```sql
WITH positioned_sub_periods AS (
    SELECT DISTINCT ON (tenant_id, division, start_date, end_date)
           tenant_id,
           division,
           start_date,
           end_date,
           sequence
    FROM periods
    WHERE division <> 0
      AND sequence IS NOT NULL
    ORDER BY tenant_id, division, start_date, end_date, sequence
)
UPDATE subject_enrollment_exceptions
SET ordinal = positioned_sub_periods.sequence
FROM positioned_sub_periods
WHERE subject_enrollment_exceptions.tenant_id = positioned_sub_periods.tenant_id
  AND subject_enrollment_exceptions.division = positioned_sub_periods.division
  AND subject_enrollment_exceptions.start_date = positioned_sub_periods.start_date
  AND subject_enrollment_exceptions.end_date = positioned_sub_periods.end_date;
```

* Conservative by construction: only an **exact** `(start_date, end_date)` match against a
  **positioned** sub-period in the **same tenant and division** is touched. Everything else stays
  NULL — unmatched span, shifted span, open bound (`NULL = x` is never TRUE), a tenant that never
  periodised, a free window.
* `division <> 0` on the period side is also what keeps the entity invariant intact: the
  exception's division must equal the matched period's, so no exception on `AcademicYearDivision.None`
  can be given an ordinal here.
* `DISTINCT ON … ORDER BY … sequence` is one deliberate addition beyond the brief's letter (see
  *Deviations*): an `UPDATE … FROM` with more than one match picks arbitrarily, and the backfill
  must be the same on every re-run.

migrationBuilder.DropIndex(

migrationBuilder.DropColumn(

### Why the row is gated on the parent, not on `IsSubPeriod`

`PeriodFormFields`'s existing `IsSubPeriod` parameter is only ever set on the **create** path
(`PeriodUpsert.InitializeCreateAsync`); `InitializeEditAsync` loads the parent into

row in **edit mode** — precisely where an existing sub-period needs its position changed. The row is
therefore gated on `Guid.TryParse(Model.ParentPeriodIdText, out _)`, which is the same thing the
entity's `ValidateSequence` and the filtered index key on, and which holds in both create and edit.

## Deviations from the brief (all deliberate, all small)

1. **`DISTINCT ON` in backfill 2.** The brief specified an equality match; I made the match
   deterministic when two positioned sub-periods of one tenant happen to share a span (two
   overlapping academic years). Without it Postgres would pick an arbitrary match. Lowest sequence
   wins; the statement is stable across re-runs.
2. **Two extra call sites that would otherwise have silently destroyed data** (not in the brief's
   file list):
   * `UpdatePeriodHandler` — the existing `period.Update(...)` call had to receive
     `command.Sequence`; otherwise *every* period edit would clear the new column.
   * `PeriodSubPeriodsEditor.razor` (the inline sub-period grid) — its
     `UpdatePeriodRequest` now echoes the row's `Sequence` (`StartEdit` captures it,
     `ResetInlineFields` clears it). Without this, renaming or re-dating a sub-period from the
     year's own editor would unposition it. The inline grid still does **not offer** a position
     (that row is `PeriodFormFields`'s, per the brief).
3. **`Down()` column order.** EF generated `DropIndex → DropColumn ordinal → DropColumn sequence`;
   I reordered the two independent column drops to `sequence → ordinal`, the strict reverse of the
   `AddColumn` order, because ef-migrations rule 4 asks for the inverse order. The index still goes
   first, as the brief requires.
4. **Extra guards, not extra features**: the digit-run length guard in the name cast (a >9-digit
   run would abort the migration with `value out of range`), the "include the current position"
   extension of the dropdown options (a bound value absent from `Items` is silently dropped by
   `DropdownComponent` on save), and the 11th–13th ordinal-suffix case.
5. **The brief's 41-byte index name is actually 42 bytes** (`wc -c`). Immaterial — both are inside
   the 63-byte limit, which is the property being checked.

Nothing in slices 5/6 was touched, no new endpoint was added, no `Program.cs` change, no AppHost or
feature-flag change, no spec or round-doc edit.

## Residual risks / what I could not verify

1. **A duplicate period position is a 500, not a 4xx.** `POST /students/periods` and
   `PUT /students/periods/{id}` with a position already held by a sibling sub-period hit the
   filtered unique index and surface as an unhandled `DbUpdateException` → 500 (the routes catch
   only the `Period*Exception`s, `ArgumentException` and `ConcurrencyException`). The plan's slice 3
   lists no duplicate guard for periods, so I did not add one — and I did not silently add a 409/422
   either. The UI row offers 1st–4th regardless of what is already taken, so this is reachable from
   the new control. The index still prevents the bad data (see the collision run above). **This is
   the one thing I would want an owner decision on**: either a 422 pre-check in
   `CreatePeriodHandler`/`UpdatePeriodHandler` (mirroring the exception handler's
   `ExistsAsync` → 409 pattern) or filtering the already-taken positions out of the dropdown. Both
   are small; both are outside the brief as written.
2. **The backfill assumes sane names.** Two sibling sub-periods that both end in the same integer
   (`"Term 1"` and `"Term 01"`) abort the migration at `CREATE INDEX`. Loud and data-preserving, but
   it means the migration is not unconditionally applicable to arbitrary dev data. Production data
   is unreleased/new for these columns, so the exposure is dev/staging only.
3. **`SubPeriodDefinitionRequest` has no `Sequence`.** The atomic year+sub-periods create and the
   inline grid's "Auto-split" therefore create *unpositioned* sub-periods (NULL), which is legal.
   If the round wants those positioned, that is a further slice-3/4 decision (assigning 1..N to an
   auto-split would be one line, but it is a product choice).
4. **No end-to-end assertion of the new fields.** Nothing yet asserts that posting
   `sequence`/`ordinal` persists and reads back through the API — that is slice 6's "new ordinal
   coverage". I verified the wiring statically (same JSON property name on client record, command
   and DTO; named arguments at every construction site) plus the unit/integration suites, but I did
   **not** write that test.
5. **`LabelPosition.Below` is unverified visually.** No browser pass was possible here; the CSS is
   reasoned and additive (and the CSS/source tests in `Admin.Tests.Unit` are green), but nobody has
   looked at a row rendered with the label beneath its input. Nothing in slices 2–4 uses
   `Below` yet — slice 5 is the first caller.
