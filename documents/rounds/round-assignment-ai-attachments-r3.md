  `StageAttachmentCommandHandler` immediately after `StoreAsync`: the bytes are in hand, it runs outside the

### The AI contract extension *(P1-1)*

`QuestionGenerationResponse` carries only `Questions`, and `IAssignmentQuestionGenerator.GenerateAsync` returns
only `IReadOnlyList<GeneratedQuestionDto>` — so the resolved `(provider, model)` is computed
(`AssignmentQuestionGenerationService.cs:62-66`) and **discarded**. The Assignments host **cannot** resolve it

### The generation-header write point and `GenerationId` propagation *(P1-2)*

Today's question sync is snapshot → `RemoveQuestion` → `AddQuestion`, which **re-mints every row with a new `Id`**
(`UpdateAssignmentCommandHandler.cs:79-101`; `ConfirmQuestionsDraftCommandHandler.cs:53-54` mirrors it). Without
explicit handling, an author's first save silently strips provenance from every generated question.

1. **Write point:** at **draft-stage / generate time**, through an **Assignments.Api command** carrying the
   requested shape plus P1-1's resolved provider/model. One row per generation, written by the host that owns the
   assignment, so the AI host stays stateless.
2. **Propagation:** `GenerationId` rides every hop — `NewQuestionDto` in the staged draft JSON, and the
   create/update question DTOs — into a new `AddQuestion(..., Guid? generationId)` overload. The sync path must
   **preserve** the id rather than dropping it on re-mint.

### The attachment extraction round-trip *(P1-3)*

`Assignment.AddAttachment` mints new rows on every save (`Assignment.cs:583`), so persisted extraction fields are
**wiped by the next save** unless carried. **Required:** extend `StagedAttachmentDto` (`ContractTypes.cs:467`) and
the create/update attachment DTOs with the extraction outcome (mirroring how `StoragePath` already rides along),
and **validate inbound text length server-side** because it round-trips through the client.

### The grounding budget *(P1-6)*

`AssignmentQuestionGenerationService.cs:31-35` **hard-rejects** `> 5` entries and `> 20000` chars each with a 400,
and URL texts already consume up to 3 slots (`QuestionGenerationSection.razor:164-173`). Attachments must **share**
that budget; extending it would contradict D1's "existing seam" and criterion 6's byte-equivalence claim.

**Merge policy:** URL texts first, attachment texts fill the **remaining** slots up to 5, each truncated to
`MaxResourceTextLength`, with a per-attachment fail-open **drop** when slots run out. **Consequence: no AI-host
constant change is needed at all** — the only AI-host change is P1-1.

### Acceptance criteria (discriminating against `0c8912da` unless marked)

1. **Extraction — real formats.** A PDF and a DOCX with known text each yield that text; a corrupted/truncated file
   and an unsupported content type each yield a **failed/unsupported status with the attachment intact and the
   request succeeding** (fail-open), never an exception that fails the upload.
2. **Extraction — safety.** An extract that would exceed the character ceiling **stops early** (assert on work
   done, not just stored length — a zip bomb must not be materialized); a file **above the extraction-specific
   cap** is `Unsupported` **without parsing** (distinct from the pre-existing 25 MiB stage refusal); a **correct
   extension with wrong magic bytes** is `Failed`/`Unsupported`, never trusted.
3. **Persistence — attachment round-trip.** Extraction fields persist and **survive a create/update save cycle**
   (the full-replacement trap) — asserted on real Postgres after a save that re-mints the attachment rows.
4. **Persistence — generation.** Every generation writes exactly **one** header row recording the requested shape
   and the **server-resolved** provider/model (P1-1), and its produced questions carry that `GenerationId`
   **after a save** (P1-2), asserted on real Postgres.
5. **Regeneration.** A user-triggered regenerate **replaces** the stored extraction for that attachment (no
   duplicate rows, status transitions correctly) and is the *only* thing that rewrites it — a second generate does
   not silently re-extract.
6. **AI-from-attachments — presence-asserted** *(plan-review P2-1: the old wording was vacuous)*. With two
   attachments, one unreadable, the captured request carries the **readable** one's extracted text inside
   `ResourceTexts` within the shared budget; without attachments the request is byte-equivalent to today's.
7. **Action wiring — regression guard, NOT a discriminator** *(P2-2)*. The kebab action still anchors to the
   compartment generator (AI-2) and the gate still renders disabled-with-reason (AI-4). Both already exist at
   `0c8912da` (delivered by R1), so this **cannot fail against the base** and is recorded as a regression guard.
8. **Tenancy.** A generation header cannot be read across tenants, and carries the `(TenantId, AssignmentId)`
   index per module convention.

### ⚠️ Scope exception — a pre-existing P0 repair rides in this round (authorised by the supervisor)

**Defect (reproduced at `0c8912da` with this diff absent):** on PostgreSQL, owned children could not be **added**
to a persisted assignment. `AssignmentConfiguration` declared `HasKey(x => x.Id)` on all four owned types but never
`ValueGeneratedNever()`, so the `Guid` key kept the `ValueGeneratedOnAdd` convention and EF Core read an
explicitly-set key on a newly-attached owned instance as an **existing** row: state `Modified`, SQL
`UPDATE assignment_attachments … WHERE id = <new id>` with **no INSERT** → 0 rows → `DbUpdateConcurrencyException`.

**Blast radius:** `AssignmentAttachment`, `AssignmentQuestion`, `QuestionOption`, `AssignmentReview` — i.e. adding
or replacing any question, attachment, option or review on a persisted assignment failed outright. **InMemory
performs no row-count check, so the entire unit suite was blind to it** — the same false-green shape the round's
Integration suite exists to prevent.

**Fix:** `ValueGeneratedNever()` on all four owned keys, with a load-bearing comment at the site. **No migration**
— `dotnet ef migrations has-pending-model-changes` reports *"No changes have been made to the model since the last
migration."* **Guarded by** `OwnedChildInsertPostgresTests` (4 tests), which assert the row is present when read
back from a **fresh context** (not merely "no exception escaped") and which threw `DbUpdateConcurrencyException` at
base. Recorded in **§17** with root cause + blast radius, and flagged here for the diff reviewer.

### Residual risks disclosed

1. **PDF single-page decompression** — `GetPages()` is lazy per *page*, so an adversarial PDF whose *individual*
   page content stream is itself a bomb is bounded only by the 10 MiB input cap and the timeout. Same shape as (2).
2. **DOCX single-run size** — `OpenXmlReader.GetText()` materialises one element at a time; a document whose single
   `<w:t>` decompresses to hundreds of MB is bounded by the ceiling only *across* elements. The realistic
   many-element bomb is proven early-aborting.
3. **Orphaned parse task on timeout** — the abandoned `Task.Run` keeps running (neither library accepts a token);
   its result is discarded and the pool thread is released when the parse finishes, contained by the 10 MiB cap.
4. **Duplicate assignment drops extraction** — `DuplicateAssignmentCommandHandler` copies attachments as
   `NotAttempted` (correctly: the provenance belongs to the original), so a duplicate reads "Not read yet" until
   the author clicks Re-read. One click; not covered by a test.
5. **Timeout is the only configurable extraction knob** (default 15 s); the caps are compile-time by design.
