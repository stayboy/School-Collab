## Summary

Introduces the central `SchoolCollab.Config` bounded context — the new owner of runtime feature flags — and ships three production bug fixes uncovered while wiring it up.

The Config context exposes global defaults + per-tenant overrides with full CRUD, audit, and resolve endpoints (`/api/features/global` and `/api/features/{tenantId}`). The Admin gets a new config-flags Razor module, and the Aspire AppHost wires `config-api` + `config-db` and fans the `outbox-exchange-config` parameter out to it. The MigrationService runs the Config migrations and seeds the runtime flag on first run.

This is the implementation described in `documents/solution/central-config-service-plan.md` (the "Finding → Implementation" notes) and supersedes the old `centralized-feature-flags-implementation` approach (the HTTP-overlay variant was removed earlier in #48; this PR replaces that with a first-class bounded context).

## Production bug fixes

### 1. MigrationService `FEATURE:EnableCodedValuesAiChat` seeder re-run crash

`SchoolCollab.MigrationService/Program.cs` performed the existence check with the raw key string:

```csharp
const string key = "FEATURE:EnableCodedValuesAiChat";
... f.Key == key
```

But `FeatureFlag.Create(...)` persists the key via `NormalizeKey(...)`, which upper-cases the area after the `FEATURE:` prefix. Postgres text comparison is case-sensitive, so the equality check missed the existing row on re-run and the subsequent INSERT violated the partial unique index `ix_feature_flags_key_unique` — blocking the API host (`migrator` is `WaitForCompletion` for every API).

Fix: use `FeatureFlag.NormalizeKey("FEATURE:EnableCodedValuesAiChat")` in the existence check so it matches the canonical stored form. Adds 3 regression tests in `tests/SchoolCollab.Config.Tests.Unit/FeatureFlagKeyNormalisationTests.cs`:
- `NormalizeKey_Uppercases_Area_After_Feature_Prefix` — pins the `NormalizeKey` contract
- `Existence_Check_With_Canonical_Key_Finds_Previously_Seeded_Flag` — confirms the fix
- `Existence_Check_With_Mixed_Case_Key_Misses_Normalised_Storage` — documents the original bug

### 2. Config API `Cannot resolve scoped service from root provider`

`AddConfigCore` registered **both** `AddDbContextFactory<ConfigDbContext>` and `AddDbContext<ConfigDbContext>`. The second registration overwrites `IDbContextOptionsConfiguration<ConfigDbContext>` as **Scoped**, which then fails to resolve from the application service provider used by EF Core's `CreateDbContextOptions` — breaking `GET /api/config/flags` with a 500.

Fix: keep only `AddDbContextFactory<ConfigDbContext>`. EF Core's factory registration already exposes `ConfigDbContext` as Scoped (handlers that inject the context directly keep working), and the `IDbContextOptionsConfiguration` stays Singleton. This matches the pattern used by `AddCodedValuesCore`. The endpoint now returns the expected flag JSON and the `OutboxDispatcher<ConfigDbContext>` runs cleanly.

### 3. Config API had no `FeatureFlags:FEATURE:DisableOIDCAuth` so `/api/config/flags` was auth-gated in dev

The Config API was missing the `FeatureFlags:FEATURE:DisableOIDCAuth: "true"` setting that every other API project carries in its `appsettings.json`. With the default OIDC scheme enabled, `GET /api/config/flags` required a real authenticated user — the Admin's `ConfigFlagsApiClient.ListAsync` call would always 500, so the `/config-flags` landing page could not load.

Fix: add `src/Config/SchoolCollab.Config.Api/appsettings.json` mirroring the other API projects. Matches `.github/merge-policy.md` ("the one flag that remains deployment-time — `FEATURE:DisableOIDCAuth` — is read by each consumer from its own `appsettings.json` (dev default `'true'`)"). Verified: `GET https://localhost:52365/api/config/flags` returns the seeded `FEATURE:ENABLECODEDVALUESAICHAT` row in JSON.

### 4. Config Flags admin UI showed "a task was canceled" and swallowed real HTTP/JSON errors

Two independent problems in the new Config Flags admin pages:

- **DTO mismatch**: `ConfigFlagsApiClient.FeatureFlagDto.Kind` was declared as `string` on the client, but the Config API serializes the server-side `FlagKindDto` enum as a JSON number (`0` for `Boolean`) with no `JsonStringEnumConverter`. System.Text.Json cannot deserialize `0` into a `string`, so the landing-page list call failed during JSON parsing.
- **`ContinueWith(OnlyOnRanToCompletion)` swallowed faults**: every method in `ConfigFlagsApiClient` wrapped `GetFromJsonAsync`/`PostAsJsonAsync` in `ContinueWith(..., TaskContinuationOptions.OnlyOnRanToCompletion)`. When the antecedent task faulted (e.g., the JSON deserialization error above), the continuation was *canceled* and the original exception was unobserved. The Blazor page therefore saw only a `TaskCanceledException` with the generic message "A task was canceled", hiding the real failure.
- **Prerender cancellation surfaced in the UI**: `ConfigFlags/Index.razor` caught `OperationCanceledException` only when `ct.IsCancellationRequested && !_disposed`. During Blazor Server prerendering the component is disposed before the in-flight `LoadAsync` completes, so `_disposed` was already `true`, the `when` filter rejected the catch, and the cancellation propagated to the `ErrorBoundary` — also displaying "A task was canceled".
- **Detail page double-escaped route keys and hid load failures**: `ConfigFlagDetail.razor` passed `Uri.EscapeDataString(Key)` to `ConfigFlagsApiClient` methods that already escape the key, and any load exception was swallowed without surfacing an error to the operator.

Fix:
- Add a client-side `FlagKindDto` enum (`Boolean = 0`) and change `FeatureFlagDto.Kind` from `string` to `FlagKindDto`; configure `JsonSerializerOptions` with `JsonStringEnumConverter<FlagKindDto>` for both request and response serialization.
- Rewrite every `ConfigFlagsApiClient` method with `async/await` and explicit `EnsureSuccessStatusCode`/`ReadFromJsonAsync` calls, removing all `ContinueWith(OnlyOnRanToCompletion)` wrappers so real HTTP/JSON errors propagate correctly.
- Catch `OperationCanceledException` unconditionally in `ConfigFlags/Index.razor.LoadAsync`; prerender disposal and superseded loads no longer render "A task was canceled".
- Remove redundant `Uri.EscapeDataString` calls in `ConfigFlagDetail.razor` and add `_loadError` display so API failures are visible instead of silently looking like "Flag not found".

Adds 3 regression tests in `tests/SchoolCollab.Admin.Tests.Unit/ConfigFlagsApiClientTests.cs`:
- `ListAsync_DeserializesServerDto_WithEnumKind_AsBoolean` — confirms the `FlagKindDto` enum round-trips from the server's numeric JSON.
- `ListAsync_PropagatesHttpError_InsteadOfSwallowingAsCancellation` — ensures a 500 from the API is surfaced as `HttpRequestException`, not a misleading `TaskCanceledException`.
- `GetAsync_ReturnsNull_ForNotFound` — verifies 404 is handled gracefully.

## Related

- Closes the `FEATURE:ENABLECODEDVALUESAICHAT` seeder crash that blocked every API from starting under the Aspire AppHost.
- Closes the `GET /api/config/flags` 500 caused by the dual `AddDbContext` / `AddDbContextFactory` registration.
- Closes the `GET /api/config/flags` 500 caused by the missing dev-default `DisableOIDCAuth: true` setting in the Config API.
- Adds a settings entry point (toolbar icon → `/settings` dashboard → Config Flags) so operators can reach the new feature-flag admin UI without going through the left-hand nav.
- Closes the Config Flags landing-page "a task was canceled" error caused by the client DTO/serialization mismatch, the `ContinueWith(OnlyOnRanToCompletion)` fault-swallowing pattern, and the prerender cancellation handling in `ConfigFlags/Index.razor`.
- Closes the all-caps feature-flag key display by preserving the area casing in `FeatureFlag.NormalizeKey` and rendering the key with `Humanizer` as a clickable `FluentAnchor`.
