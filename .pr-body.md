## Summary

Introduces the central `SchoolCollab.Config` bounded context — the new owner of runtime feature flags — and ships two production bug fixes uncovered while wiring it up.

The Config context exposes global defaults + per-tenant overrides with full CRUD, audit, and resolve endpoints (`/api/features/global` and `/api/features/{tenantId}`). The Admin gets a new config-flags Razor module, and the Aspire AppHost wires `config-api` + `config-db` and fans the `outbox-exchange-config` parameter out to it. The MigrationService runs the Config migrations and seeds the runtime flag on first run.

This is the implementation described in `documents/solution/central-config-service-plan.md` (the "Finding → Implementation" notes) and supersedes the old `centralized-feature-flags-implementation` approach (the HTTP-overlay variant was removed earlier in #48; this PR replaces that with a first-class bounded context).

## Production bug fixes

### 1. MigrationService `FEATURE:EnableCodedValuesAiChat` seeder re-run crash

`SchoolCollab.MigrationService/Program.cs` performed the existence check with the raw key string:

```csharp
const string key = "FEATURE:EnableCodedValuesAiChat";
... f.Key == key
```

But `FeatureFlag.Create(...)` persists the key via `NormalizeKey(...)`, which upper-cases the area after the `FEATURE:` prefix. Postgres text comparison is case-sensitive, so the equality check missed the existing row on re-run and the subsequent INSERT violated the partial unique index `ix_feature_flags_key_unique` — blocking the API host (`migrator` is `WaitForCompletion` for every API).

Fix: use `FeatureFlag.NormalizeKey("FEATURE:EnableCodedValuesAiChat")` in the existence check so it matches the canonical stored form. Adds 3 regression tests in `tests/SchoolCollab.Config.Tests.Unit/FeatureFlagKeyNormalisationTests.cs`:
- `NormalizeKey_Uppercases_Area_After_Feature_Prefix` — pins the `NormalizeKey` contract
- `Existence_Check_With_Canonical_Key_Finds_Previously_Seeded_Flag` — confirms the fix
- `Existence_Check_With_Mixed_Case_Key_Misses_Normalised_Storage` — documents the original bug

### 2. Config API `Cannot resolve scoped service from root provider`

`AddConfigCore` registered **both** `AddDbContextFactory<ConfigDbContext>` and `AddDbContext<ConfigDbContext>`. The second registration overwrites `IDbContextOptionsConfiguration<ConfigDbContext>` as **Scoped**, which then fails to resolve from the application service provider used by EF Core's `CreateDbContextOptions` — breaking `GET /api/features/global` with a 500.

Fix: keep only `AddDbContextFactory<ConfigDbContext>`. EF Core's factory registration already exposes `ConfigDbContext` as Scoped (handlers that inject the context directly keep working), and the `IDbContextOptionsConfiguration` stays Singleton. This matches the pattern used by `AddCodedValuesCore`. The endpoint now returns the expected flag JSON and the `OutboxDispatcher<ConfigDbContext>` runs cleanly.
